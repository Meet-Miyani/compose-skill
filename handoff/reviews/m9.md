## Owner decision O-12: fix the class, then a fresh held-out set

**Required changes (worker, "M9-fix"):**

K1. **One "proportional, plain-spoken senior" rule set**, stated **once** in the `compose-architecture`
    operating stance and linked from `compose-feature/references/review-mode.md` and the pushback
    guidance in the other skills. It is non-negotiable, because it is about behaviour, not code
    internals:
    1. **Talk in plain engineering reasons.** In user-facing answers, explain *why* in one plain
       sentence. Never list rule numbers or section IDs. A rule or case name may appear once in
       parentheses when it helps the reader find it.
    2. **Scale the answer to the request.** Fix what is wrong and keep what works.
       - A review separates **blocking** (bugs, contract breaks) from **worth doing later**, and says
         what is fine as it is.
       - The smallest correct change wins.
    3. **Reuse before rebuild.** Extend the existing repository, mapper or screen. Never rebuild a
       slice to put it "in kit shape" unless asked.
    4. **Pushback is short and constructive.** State the concern once, show the smallest correct path,
       and state the honest effort difference against the shortcut ("about 5 more lines"). Then deliver
       it (stance item 3).

    Red flags to add:
    - "I'll cite every rule this touches"
    - "Everything here is a blocker"
    - "I'll rebuild it the kit way"
    - "I'll explain the rules before the fix"

    Keep SKILL.md within the 5,000-token max. Move detail to a reference if needed, per the growth
    policy.
K2. **iOS Flow interop (`compose-platform/references/ios-swift-interop.md`).** When exposing a flow to
    Swift, state:
    - `StateFlow` (current value; the natural fit for UI) versus a cold `Flow` (no initial value; needs
      an explicit collection lifecycle)
    - that collection is tied to the Swift owner's lifecycle
    - that UI-bound values are delivered on the main thread

    Verify against the fetched SKIE docs or the official KMP iOS interop page.
K3. **D9-1.** Every platform-provided binding (e.g. the DataStore file path) is supplied for **every
    target the project declares**; otherwise the Koin compiler plugin fails the iOS link. One line in
    `compose-data/references/datastore.md` and in the `compose-platform` platform-binding rule.
K4. **Rubric fix, FEAT-01b craft item.** "None on Screen" becomes "not required on Screen/leaf
    composables; a one-line KDoc there is fine; bloated or noise KDoc fails". Sync `scenarios.md` and
    `evals.json`.
K5. **Demote held-out v1.** Move `evals-v2/heldout.json` and `evals-v2/heldout.md` to
    `evals-v2/heldout-v1-dev.json` and `.md` (a plain rename). They become extra dev scenarios. From now

## Fix round 2 of 2 (STANDARDS §8.5 rule 4); required changes

L1. **Silent procedure** (compose-architecture stance; linked from every skill that routes or verifies):
    - Change "state the case, read the owning skill" to "decide the owning skill and the project case
      **silently**".
    - Add one non-negotiable: "Routing, case classification, rule lookups and verification gates are
      internal steps. Never open with them or print them. Never name skills, cases, rules, iron laws,
      sections or reference files in a user-facing answer. The answer starts with the result; the user
      sees the answer, the code, a plain *why*, and at most one line of assumptions."
    - Verification checklists are run, not printed. Report only failures, in plain words.
    - Red flags to add:
      - "Owning skill: … / Case 1 …" as an opening line
      - "I'll show my verification checklist"
    - Update every workflow step and template phrase that says "state …" or "report yes/no" so it no
      longer instructs printing.
L2. **Review severity policy** (compose-feature `review-mode.md`, stated once and linked):
    - **Blocking** covers only: a user-visible bug, a crash or ANR risk, data loss, a security or privacy
      issue, or anything that fails the build, tests or guards.
    - A kit-convention deviation in working code (naming, file layout, two first-load owners with no
      bug, DI style) is **"worth doing later"**, unless the task is kit adoption or the user asked for a
      convention review.
    - "Not shippable" or "request changes" is used only when a blocking item exists.
    - Every review includes a short **"fine as is"** line.
    - Output shape:
      1. verdict
      2. blocking (usually 0–2)
      3. worth doing later
      4. fine as is
    - Update any rubric wording in the **dev** scenarios that assumed every deviation is blocking, and
      keep `scenarios.md` and `evals.json` in sync.
