## Fix round 2 of 2 (STANDARDS §8.5 rule 4); required changes

L1. **Silent procedure** (compose-architecture stance; linked from every skill that routes or verifies):
    - Change "state the case, read the owning skill" to "decide the owning skill and the project case
      **silently**".
    - Add one non-negotiable: "Routing, case classification, rule lookups and verification gates are
      internal steps. Never open with them or print them. Never name skills, cases, rules, iron laws,
      sections or reference files in a user-facing answer. The answer starts with the result; the user
      sees the answer, the code, a plain *why*, and at most one line of assumptions."
    - Verification checklists are run, not printed. Report only failures, in plain words.
    - Red flags to add:
      - "Owning skill: … / Case 1 …" as an opening line
      - "I'll show my verification checklist"
    - Update every workflow step and template phrase that says "state …" or "report yes/no" so it no
      longer instructs printing.
L2. **Review severity policy** (compose-feature `review-mode.md`, stated once and linked):
    - **Blocking** covers only: a user-visible bug, a crash or ANR risk, data loss, a security or privacy
      issue, or anything that fails the build, tests or guards.
    - A kit-convention deviation in working code (naming, file layout, two first-load owners with no
      bug, DI style) is **"worth doing later"**, unless the task is kit adoption or the user asked for a
      convention review.
    - "Not shippable" or "request changes" is used only when a blocking item exists.
    - Every review includes a short **"fine as is"** line.
    - Output shape:
      1. verdict
      2. blocking (usually 0–2)
      3. worth doing later
      4. fine as is
    - Update any rubric wording in the **dev** scenarios that assumed every deviation is blocking, and
      keep `scenarios.md` and `evals.json` in sync.

### F-A-3: stale lambda-memoization rule in `compose-ui/references/lists.md` (REAL kit defect)

- **The rule.** `lists.md` line 73 (source tag SKY-59) says: "There is no auto-memoization inside lazy
  item builders: hoist stable lambdas by hand instead of allocating a fresh closure per item per
  composition."
- **The official page contradicts it.** Strong skipping mode
  (https://developer.android.com/develop/ui/compose/performance/stability/strongskipping, fetched
  2026-09-26):
    - "With strong skipping enabled, every lambda inside a composable function will be automatically
      remembered."
    - The lambda is keyed with its captures.
    - Strong skipping is enabled by default in Kotlin 2.0.20.
- **The rule doesn't hold for item content either.** Lazy item content is a `@Composable
  LazyItemScope.(T) -> Unit` lambda, so the general rule covers it. The kit pins Kotlin 2.4.
- **The evidence on H3-05.** Five of six kit answers (Muse, DeepSeek V4.1 Flash, MiniMax, DeepSeek V4
  Pro, Sonnet) repeated the claim as a finding, several as **blocking**.
    - Most then "fixed" it with `remember(exercise.id, …) { { … } }`, which can hold a stale capture
      that automatic memoization (keyed on the captured `exercise`) would not.
    - Opus without the kit got it right ("remembered automatically based on its captures").
    - Opus + kit worded it as a stale-capture concern, not an allocation blocker.
- **Class:** a stale third-party rule harvested from a pre-strong-skipping source. That is exactly what
  the P11 freshness loop and "library source decides" exist to catch.
- **Fix (queued; worker-written; applied after the option A panel finishes, so every panel model runs
  the same frozen kit):**
    1. Rewrite `lists.md` rule 73: under strong skipping (the default from Kotlin 2.0.20), lambdas in
       item content are auto-remembered by their captures. Hand-hoisting is not a finding.
    2. Sweep every skill for other pre-strong-skipping claims: lambda hoisting, `remember` around
       callbacks, and "unstable lambda" wording.
    3. Add a review-mode guard: never flag lambda allocation in composables as blocking when the Kotlin
       version is 2.0.20 or later.
    4. Verify on a fresh review scenario (not H3-05).

### R1: F-A-3, stale lambda-memoization rule (compose-ui; review mode)
